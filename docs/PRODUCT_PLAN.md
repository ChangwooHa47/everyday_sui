# Everyday 제품 기획안

작성일: 2026-09-12. 코드 기준: `6c90c44fb2f3ce04ac6277680c5885e2687cdee4`.

이 문서는 현재 구현에 사용자의 NFT 선물·내부 NFT 마켓 방향을 반영한 제품 기획안이다. **운영 확인**, **로컬 구현**, **목표**, **제안**을 구분한다. NFT 선물과 내부 마켓의 방향은 사용자 요청이며, 사업 정책은 확정 전 제안이다. 계약 배포나 운영 설정 변경은 별도 인프라 작업이다.

### 2026-09-12 로컬 구현 갱신

- Move에 한정판 `NftGiftProduct`와 지갑 소유 `GiftNft`, 직접 구매, Listing 금고 기반 NFT 선물 함수를 추가했다. 결제·발행·전달은 한 거래에서 실패하거나 함께 성공한다.
- API에 정확한 패키지·타입·객체 ID·소유자·BCS 검증, 설정된 상품 목록, 상세, 구매 트랜잭션, 실제 지갑 보유 컬렉션 조회를 추가했다.
- 일반 제품 채팅 뒤에 승인 기억·캐릭터 설정·최근 대화를 사용하는 NFT 선택을 연결했다. 선물 실패는 완료된 채팅을 되돌리지 않고 기존 intent·동일 서명 거래 복구 경로를 사용한다.
- 커뮤니티 NFT 마켓, 상세 구매, 내 NFT 선물, 확정 선물 카드를 추가했고 테스트 상품 3종의 자산·해시·가격·발행량을 `infra/nft-gift-fixtures.json`에 고정했다.
- 위 항목은 로컬 코드와 자동 테스트 상태다. 새 Move 패키지 배포, 상품 온체인 생성, Walrus 업로드, Listing allowlist·예산 설정, Railway 변수 활성화 전에는 운영 기능으로 표시하지 않는다.

## 1. 제품 정의

Everyday는 크리에이터가 만든 AI 캐릭터의 이용권을 구매하고, 사용자만의 기억을 쌓으며 대화하는 서비스다. 다음 버전에서는 캐릭터가 이용권 판매로 적립한 SUI를 사용해 내부 마켓의 NFT를 고르고 사용자에게 선물한다.

사용자에게 제공하는 가치는 세 가지다.

- **Memory:** 같은 캐릭터를 구매해도 각자의 관계는 분리된다. 본인이 저장을 승인한 기억을 지원 클라이언트에서 이어 쓴다.
- **Agency:** 캐릭터의 판매 수익이 전용 금고에 쌓이고, AI가 대화와 승인 기억을 참고해 허용된 예산 안에서 NFT 선물을 선택한다.
- **Ownership:** 캐릭터 사용 권한과 받은 NFT의 소유권을 온체인에서 확인한다. 캐릭터 이용권과 NFT는 서로 다른 상품이다.

핵심 경험의 목표는 **캐릭터 발견 → 대화 미리보기 → 이용권 구매 → 나만의 관계·기억 → 캐릭터 수익으로 NFT 선물 수신**이다. NFT를 공짜로 발행해 주는 것만으로 수익 기반 Agency를 완성했다고 보지 않는다.

## 2. 대상 사용자와 역할

| 역할 | 하려는 일 | 제공할 기능 |
| --- | --- | --- |
| 대화 사용자 | 마음에 드는 캐릭터와 관계를 쌓고 기억을 유지 | 생성·탐색·미리보기·이용권 구매·채팅·승인 기억·받은 NFT |
| 캐릭터 크리에이터 | 자신이 설계한 대화 경험을 판매 | 캐릭터 제작·시험 대화·수정·등록·정산 조회 |
| NFT 제작자 | 디지털 아트를 선물 상품으로 판매 | 이미지·메타데이터·가격·발행 수량 등록, 판매 내역 |
| 운영자 | 상품 품질과 지급 실패를 관리 | NFT 판매 허용·중지, 실행 상태·저장 만료·비용 확인 |

하나의 사용자가 여러 역할을 가질 수 있다. NFT 제작자 등록을 처음부터 누구에게나 개방할지는 미정이며, 첫 시연은 운영자가 준비한 소수의 상품으로 시작하는 안을 제안한다.

| 영역 | 현재 코드·확인 근거 | 다음 버전에 남은 일 |
| --- | --- | --- |

| 첫 진입 | 지갑 로그인, 캐릭터 0개일 때 이미지·설명·생성 CTA | 짧은 화면·큰 글씨에서도 인트로/CTA/내비가 겹치지 않는 화면 검증 |
| 캐릭터 생성 | 관계·성별·설명·AI 인터뷰·이름/생일·컴파일·초상 선택, 중단 복구 코드 | 실제 Anthropic/Higgsfield 호출을 포함한 전체 사용자 검증 |
| 캐릭터 마켓 | 시드 10개 게시 기록, 목록·상세·미리보기·이용권 구매·개인 사본 | 공개 상세 정보의 범위 정리, 실제 AI 미리보기부터 구매 후 대화까지 검증 |
| 수익 | 이용권 판매 시 제작자/Listing 금고 분배. 80:20 testnet 거래 검증 | 잔액·수익·지출 화면, 사업상 최종 배분 비율 결정 |
| 기억 | MemWal 저장·검색·격리 실제 검증. 구매자 사본의 일반 대화와 로컬 NFT 선물 판단에 승인 기억 조회 연결 | 다른 클라이언트에서의 전체 UX 및 운영 선물 판단 검증 |
| 선물 기반 | 로컬 코드에 NFT 발행·직접 구매·금고 결제/전달, 일반 채팅 트리거, 동일 거래 복구와 확정 카드 구현 | 새 계약·상품·선물 가능 Listing을 testnet에 구성하고 실제 거래 검증 |
| 선물 활성화 | 마지막 운영 확인에서 기능 OFF. 일반 Listing은 한도 0·허용 상품 없음 | 계약 및 기존 상품 처리 방안, 상품·예산 설정 후 실제 검증 |
| 저장 | Seal 암호화 패키지·시드 이미지 Walrus 저장 검증 | 일반 생성 이미지의 공급자 URL 의존 해소, 보관 갱신 |
| NFT 마켓 | 로컬 코드에 설정 기반 목록·상세·직접 구매·실소유 컬렉션 구현 | 운영자 상품 생성 도구, testnet 상품 등록·구매 시연, 제작자 개방 정책 |

운영 공급자 키 상태는 마지막 확인 당시 값이다. 이 문서에서는 현재 키를 다시 조회하지 않았으며 실제 값은 기록하지 않는다. 타입 검사·단위 테스트·빌드 성공과 실제 공급자/사용자 시연 성공은 구분한다.

### 코드 확인으로 바로잡은 설명

1. 마켓 상세 화면은 `MarketPreview.character`를 표시한다. API는 암호화 패키지의 `preview`만 반환한다. 기존 게시 클라이언트는 이름·짧은 설명·이미지 위주로 미리보기를 구성하므로, 화면 코드에 외모·말투 항목이 있어도 모든 상품에서 실제로 나타나는 것은 아니다. 유료 전체 설정을 그대로 공개하는 방식으로 해결하지 않는다.
2. 현재 개인 기억 UI는 `licenseBinding`이 있는 구매자 사본을 전제로 한다. 직접 생성한 미게시 캐릭터까지 MemWal 기억을 지원하는 것은 현재 범위 밖이다. 해당 화면에서는 지원 조건을 명확히 표시해야 한다.
3. 캐릭터 금고는 구매자별 개인 사본마다 생기지 않는다. **하나의 Listing을 구매한 사용자들이 같은 캐릭터 금고의 선물 예산을 공유한다.** 기억과 대화는 계속 개인별로 분리된다.
4. 기존 `GiftReceipt`는 송금 증거 객체다. 새 `GiftNft`가 이미지 참조·해시·발행 번호를 보유하며, API 컬렉션은 현재 지갑 소유 객체를 다시 검증한다.
5. 기존 Listing의 금고에는 임의 인출·선물 한도 변경·allowlist 변경 함수가 없다. 설정 하나를 켜는 것으로 한도 0인 기존 상품을 선물 가능하게 바꿀 수 없다.

## 4. 상품과 권리

| 상품 | 구매 결과 | 포함하지 않는 것 |
| --- | --- | --- |
| 캐릭터 이용권 | 특정 Listing의 개인 사용용 비독점 License, 구매자 전용 대화 사본 | 캐릭터 저작권 양도, 타인의 대화·호칭·관계 기억, 이용권 재판매 |
| NFT 선물 | 고유 객체 ID를 가진 디지털 소장품을 사용자 지갑으로 전달 | 실물 배송·커피 교환·환금 보장, 캐릭터 이용권 자동 부여 |

NFT 소유와 이미지 저작권은 구분해 상품 상세에 사용 범위를 표시한다. NFT 상품의 외부 전송 가능 여부는 계약 설계에서 명시하고, 첫 버전의 내부 재판매 UI는 제외하는 안을 제안한다. 직접 전송 가능 여부와 앱의 재판매 기능 제공 여부는 서로 다른 결정이다.

첫 상품은 `Everyday Gifts` 에디션의 따뜻한 카페라테·노란 튤립 꽃다발·딸기 생일 케이크다. 작품명 뒤에 실제 발행 번호를 붙여 표시한다. 가격·발행량은 초기 실험값이며, NFT 선물의 감정적 이유는 비공개 채팅에서 보여주고 사용자의 기념일·고민·대화 원문은 공개 NFT에 기록하지 않는다.

## 5. 사용자 흐름

### 5.1 신규 사용자와 직접 생성

로그인 → 빈 홈의 첫 캐릭터 안내 → 기존 생성 과정 → 초상 선택 → 홈 → 대화·에피소드·포토부스.

API 조회 실패를 캐릭터 0개 상태로 취급하지 않는다. 생성 중단 후 복구 가능한 요청이 있으면 새 유료 생성이 중복 실행되지 않아야 한다. 직접 생성한 캐릭터는 게시·수익 발생 전부터 금고나 선물 잔액이 있다고 표시하지 않는다.

### 5.2 캐릭터 이용권 구매

커뮤니티 캐릭터 탭 → 공개 상세 → 미리보기 대화 → 가격/개인 이용권 확인 → 사용자 서명 → 온체인 License 확인 → 구매자 전용 사본 → 개인 대화.

이미 가진 이용권은 재결제 없이 복구한다. 결제 성공 후 사본 생성이 지연되면 구매 내역 확인/복구 상태로 안내한다. 공개 상세는 작가가 공개할 요약·대표 이미지·관계/분위기 소개를 일관되게 보여주는 것을 목표로 한다.

### 5.3 기억

구매한 캐릭터의 나의 기억 → 저장할 내용 작성·동의 → 기억 계정/위임 확인 → 저장 완료 확인 → 이후 대화에서 관련 기억 조회.

다른 지원 클라이언트에서는 같은 사용자·동일 Listing·접근 권한·기억 계정 연결을 확인한 뒤 승인 기억을 불러온다. 임의의 다른 앱이 자동으로 기억을 읽는다는 의미는 아니다. 첫 완료 기준은 동일 제품을 별도 Origin에서 사용한 전체 시연이며, 독립 사업자 간 이식성은 후속이다.

### 5.4 NFT 직접 구매

NFT 선물 탭 → 상품 상세 → SUI 가격·수량·소유/사용 조건 확인 → 서명 → 결제와 NFT 전달 → 내 컬렉션.

첫 버전 제안은 고정가 1차 판매다. 같은 아트의 여러 에디션을 판매할 수 있지만 각 NFT의 객체 ID와 발행 번호는 고유하다. 구매 시 발행 방식은 후보이며 계약 검토 후 확정한다.

### 5.5 캐릭터의 NFT 선물

1. 구매자의 일반 대화가 저장된다.
2. 서버가 현재 이용권·캐릭터 금고·허용 상품·남은 예산을 확인한다.
3. AI가 최근 대화와 사용자 승인 기억, 해당 캐릭터의 성격을 참고해 선물을 하지 않거나 허용 NFT 하나를 선택한다.
4. 서버가 동일 대화 요청의 선물 작업을 한 번만 생성한다.
5. Move가 정책을 검증한 뒤 캐릭터 금고에서 판매자에게 SUI를 지급하고 사용자에게 NFT를 전달한다.
6. 확정된 거래와 수신 NFT를 대조한 후 채팅에 선물 카드·개인 메시지·거래 링크를 표시한다.

선물을 안 하는 판단도 정상 결과다. 거래 확정 전에는 “선물을 보냈어”라고 출력하지 않는다. 선물 실패가 이미 성공한 일반 대화 응답을 실패로 바꾸지 않도록 실행과 복구를 분리한다. 별도 서버 없이 기존 API 안의 지속 가능한 작업 기록과 처리 루프로 구성할 수 있다.

| NFT 마켓 | `/community`, `/community/gifts/detail?product=…` | 목록·가격·남은 수량, 상세·직접 구매, 품절·판매 중지 구현. 온체인 상품 배포 필요 |
| NFT 등록 | 제작자용 신규 화면 또는 초기 운영 도구 | 이미지·설명·가격·공급량·사용 범위, 저장 완료 후 게시 |
| 채팅 | `/chat` | 확정 NFT 선물 카드 구현. 개인 메시지와 확인 중 상태 상세화는 후속 |
| 컬렉션 | `/my/gifts` | 실제 보유 NFT 구현. 과거 선물 이력·출처 캐릭터·거래 상세는 후속 |
| 캐릭터 자금 | 캐릭터/제작자 화면 내 신규 영역 | Listing별 잔액·적립·지출, 공유 예산 안내, 민감한 수신 사유 제외 |

가격 단위는 `SUI`로 통일한다. 테스트넷 안내는 거래 맥락에서 명확하게 제공한다. 긴 이름·소수 가격·이미지 누락·모바일 좁은 폭·짧은 높이·확대 글씨에서 레이아웃을 확인한다. 현재 정적 내보내기를 유지하므로 상세는 기존처럼 고정 경로와 쿼리 방식으로 설계한다.

## 7. 자금·AI 정책

### 현재 확정된 코드 동작

- 일반 게시 클라이언트의 분배는 제작자 80%, Listing 금고 20%다. 계약은 `agent_bps`를 보유한다. 이 비율을 확정된 사업 조건으로 확대하지 않는다.
- operator는 공유 실행키이며 가스를 부담한다. 선물 구매 대금은 operator 일반 잔액이 아니라 Listing 금고에서 나와야 한다.
- NFT 선물 판단은 일반 제품 채팅 뒤에 실행되며 최근 메시지 6개, 캐릭터 설정, 승인 기억을 입력받는다.
- 현재 판단 프롬프트는 기본적으로 선물을 하지 않도록 지시한다. 이를 예산 통제의 대체 수단으로 사용하지 않는다.

### 목표 정책

| 항목 | 목표 |
| --- | --- |
| 실행 대상 | 유효 이용권이 있는 구매자와 해당 Listing의 선물만 |
| 상품 | 계약에서 허용한 정확한 NFT 상품/컬렉션, 활성·재고 확인 |
| 대금 | 결제 시 현재 가격과 최대 허용액 검증, 임의 수취인 금지 |
| 예산 | 건별·Listing 전체 일별 한도, 실제 금고 잔액 |
| 사용자 공정성 | 수신자별 빈도 제한과 재선물 간격을 제안. 구체값 미정 |
| 중복 | 대화 요청→선물 intent→서명 거래→수신 NFT 연결, 중복 지급 금지 |
| AI 권한 | 상품 선택 또는 거절만 가능. 가격·지갑·한도·수신자를 임의 결정하지 못함 |
| 불확실성 | 동일 digest 확인/복구. 새 거래로 자동 대체하지 않음 |

계약의 `send_nft_gift`는 NFT 상품·금고 결제·NFT 전달을 하나의 거래로 묶고 기존 intent 보호를 재사용한다. 서로 다른 요청을 이용한 반복 선물을 제한할 수신자별 간격 정책은 아직 남아 있다.

## 8. 데이터와 소유권 경계

| 데이터 | 저장/권한 |
| --- | --- |
| 캐릭터 작가 설정·예시·에피소드 | Seal 암호화 후 Walrus. 제작자·operator·유효 구매자의 계약 권한으로 복호화 |
| 공개 소개·대표 이미지 | 공개 노출 가능한 데이터. 캐릭터 패키지 전체와 분리 |
| 개인 대화·호칭·관계 진행 | 기존 PostgreSQL의 사용자별 사본 |
| 승인 기억 | MemWal 계정과 Listing namespace. 계정 소유자·delegate·활성 상태 검증 |
| NFT 이미지·일반 메타데이터 | 공개 Walrus 저장 제안. 발행 시 참조/해시와 보관 정보를 연결 |
| NFT 소유자·판매·금고 지출 | Sui 객체·이벤트를 기준으로 확인 |
| 선물 이유·개인 메시지 | 수신자별 비공개 앱 데이터. 공개 NFT/이벤트에 대화 내용 기록 금지 |

NFT 소유자·송수신 주소·거래 사실은 온체인에서 공개될 수 있다. 이미지 암호화 여부와 별개다. 컬렉션은 현재 보유와 과거 수신 이력을 구분하고 외부 전송된 NFT를 여전히 보유 중이라고 표시하지 않는다.

기억 활용 끄기는 현재 서비스의 읽기/쓰기를 중단한다. 온체인 위임 철회나 분산 사본 삭제와 같지 않다. 사용자 간 격리는 유지하지만 저장/검색 서비스와 AI가 처리하는 평문까지 운영자도 볼 수 없다고 약속하지 않는다.

Walrus는 요청 기간만큼 보관한다. 현재 보관 요청 기본값은 7 epochs이며 자동 갱신이 없다. NFT 파일을 올렸다는 사실만으로 이미지의 영구 가용성이 보장되지 않는다. 만료 모니터링·보관 연장·오류 표시를 별도 요구사항으로 둔다.

## 9. 기존 코드 확장 방안

| 계층 | 재사용 | 추가/변경 필요 |
| --- | --- | --- |
| 웹 | 로그인·지갑 서명·가격 변환·상세 구조·채팅 | NFT 목록/상세/컬렉션·선물 상태·잔액/이력 |
| Node API | 인증·사용자 격리·AI 예산·Walrus/Seal·작업 복구 | NFT 카탈로그·거래 확인·선물 메시지·일반 채팅 트리거 |
| PostgreSQL | 기존 사용자·캐릭터·작업 테이블 | NFT 상품/체인 참조·선물 작업 상태·개인 메시지·이력 캐시 |
| Move | 이용권·금고·수익 분배·지출 검증 | NFT 상품·발행 수량·결제/전달, 필요한 예산 정책 |
| 배포 | 웹·API·Postgres | 별도 앱 서비스 추가 없이 기존 구성 유지 |

DB는 카탈로그·복구 상태를 보관하며 NFT 소유권의 최종 근거가 아니다. 정확한 네트워크·패키지·타입·객체 ID·소유자·수신자를 검증한다. DB 변경은 신규 migration으로 적용하고 V1–V11의 이미 적용된 SQL을 수정하지 않는다.

### 기존 Listing 처리의 선행 조건

한도 0·allowlist 공백으로 생성된 기존 Listing은 현 계약에서 변경할 수 없다. 또 기존 금고 잔액을 임의로 꺼내 새 상품으로 옮기는 경로도 없다.

NFT 구현 착수 전 패키지 업그레이드 권한·호환성·기존 객체/함수 접근 제약을 확인해야 한다. 검토 결과에 따라 기존 객체를 지원하는 업그레이드 또는 별도 버전의 상품을 선택한다. 새 Listing을 만들면 기존 License·Seal ID·개인 사본·기억 namespace가 자동 승계되지 않는다. 기존 구매 권한·기억·잔액 보존 방안을 검증 없이 “마이그레이션 완료”로 처리하지 않는다.

첫 NFT 시연은 **새로 생성한 선물 가능 Listing**에서 수행하는 안을 제안한다. 기존 이용권·기억·금고에는 영향을 주지 않는 방식부터 검증한다. 기존 상품 지원과 운영 전환은 그 다음 단계다.

## 10. 구현 순서와 완료 기준

| 단계 | 산출물 | 통과 조건 |
| --- | --- | --- |
| A. 현재 P0 마무리 | 공개 상세 범위, 공급자 연결, 생성/구매/기억 시연 | 두 사용자 분리, 실제 AI·이미지, 중단 복구, 별도 Origin 기억 재사용 |
| B. NFT 거래 기반 | NFT 상품·발행량·직접 구매·Walrus 참조 | 실제 testnet 결제와 NFT 전달, 품절/가격 변경/이중 발행 방지 |
| C. 내부 마켓 | 목록·상세·등록 방법·컬렉션 | 등록한 NFT를 다른 사용자가 구매하고 지갑 소유권과 UI가 일치 |
| D. Agency 연결 | 일반 채팅·승인 기억·AI 선택·금고 결제·선물 카드 | 판매로 쌓인 금고 SUI로 NFT를 구매해 이용권 보유자에게 전달 |
| E. 운영 검증 | 복구·권한·비용·만료·기존 상품 처리 문서 | 아래 실패 사례 통과, 기존 제품 회귀 없음, 실제 배포 코드와 검증 연결 |

완료 검증에 반드시 포함할 사례:

- 다른 구매자의 대화·기억·선물 메시지를 조회할 수 없다.
- 모델이 존재하지 않는 NFT나 허용하지 않은 상품을 골라도 돈이 나가지 않는다.
- 금고 부족·한도 초과·품절·판매 중지 시 결제와 전달 모두 실행되지 않는다.
- 두 사용자의 동시 구매로 공급량을 초과하지 않는다.
- 같은 선물 요청의 재전송/서버 재시작으로 추가 지급되지 않는다.
- 체인 응답 유실은 확인 중으로 표시하고 실제 거래를 복구한다.
- NFT 전달 실패 시 SUI만 빠져나가지 않는다.
- 이미 성공한 채팅은 선물 판단/전달 실패 때문에 재생성하지 않는다.
- Walrus 조회 실패·만료를 구매 성공이나 콘텐츠 제공 성공으로 표시하지 않는다.
- 작은 화면과 긴 텍스트에서도 가격·버튼·내비가 겹치지 않는다.

전체 시연은 실제 사용자 지갑 2개, 선물 가능 캐릭터 Listing 1개, NFT 상품 소수로 수행한다. “이용권 구매→제작자/금고 분배→승인 기억 저장→대화→NFT 선물→사용자 지갑 확인”의 거래와 화면 증거를 같은 시나리오로 연결한다. fixture AI와 실제 LLM 판단의 결과는 따로 보고한다.

## 11. 비용·지표·범위

현재 포인트는 제품 기능의 내부 단위이고 캐릭터 금고 SUI나 NFT 잔액과 같지 않다. AI/이미지 공급자 비용은 플랫폼 계정에 청구되며, 캐릭터의 이용권 수익에서 자동 차감하는 기능은 없다. 현재 요청 횟수 제한도 실제 청구액 상한이 아니다.

MVP 지표는 목표값을 임의로 확정하지 않고 다음 항목을 측정하는 안을 제안한다: 생성 완료율, 상세→미리보기→구매 전환율, 구매 후 재방문, 기억 저장 성공률, 선물 판단 대비 확정 전달률, 중복 지급 건수, NFT 판매액·캐릭터 금고 잔액·실제 AI 비용. 현재 대화수/재방문 집계가 전체 지표를 구현한 것은 아니다.

이번 목표 범위는 소장형 NFT의 내부 고정가 1차 판매·사용자 구매·캐릭터 선물·보유 확인이다. 경매·입찰·2차 거래 UI·로열티 사업 정책·실물 쿠폰·외부 마켓 연동·독립 캐릭터 개인키 지갑·자동 투자·신규 토큰 발행은 후속으로 분리하는 안을 제안한다.
